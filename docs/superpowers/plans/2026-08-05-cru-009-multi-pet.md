# CRU-009 Multiple Pets — Implementation Plan

**Decisions:** [ADR 0015](../../adr/0015-pulling-multi-pet-groundwork-forward.md) is the checklist for
this ticket, not background reading. It names the four call sites that must move together and says
why. Read it first.

Also read `CONTEXT.md` (**Pet**, **Feeding Schedule**, **Activity**) and `AGENTS.md`.

**Branch:** `feat/CRU-009-multi-pet`, off `main`, already created and clean.

**Goal:** a household can hold several pets. You can add one, see all of them on Home, open any of
them, and remove one. Today the app creates exactly one pet in onboarding and can never make another.

## The shape, decided

**No active-pet selector.** Home shows every pet, one section each. There is no global "selected pet"
state, no store, no persistence, and no rule needed for what happens when the selected pet is
deleted.

ADR 0015 anticipated a selector at the top of **pet detail**. That is not needed either: pet detail
already routes by `petId`, and you reach it by tapping a pet on Home.

The consequence to accept: Home gets taller with each pet. Fine at two or three, scrolls at six.

## What this ticket is not

**It does not redesign Activity.** That screen is under question — Dylan's read is that a history of
past feeds is the weakest surface in the app, and it may become something forward-looking instead.
That is a separate conversation and must not be started here.

But Activity **cannot be left untouched**, and this is the trap in this ticket: it currently calls
`useFeedLogs(pet?.id)` where `pet` is the oldest pet. The moment a second pet exists, that pet's
entire feed history is silently invisible. Task 9 is the minimum change that stops it lying. It is
not a redesign and must not grow into one.

**No paywall.** PRODUCT_BRIEF has free = one pet. Building it without a limit on purpose; the limit
comes later.

## Task 1 — `add_pet()`

Migration `20260806090000_add_pet_rpc.sql`.

A pet without a Feeding Schedule is a pet the app cannot do anything with — no slots on Home, no
Missed Feed detection. So the pet and its schedule are created together or not at all, exactly as
onboarding does it.

```sql
create or replace function public.add_pet(
  pet_name text,
  pet_breed text,
  pet_sex public.pet_sex,
  pet_birthdate date,
  pet_birthdate_is_approximate boolean,
  pet_photo_url text,
  feeding_times jsonb
)
returns public.pets
language plpgsql
security invoker
set search_path = ''
as $$
declare
  target_household_id uuid;
  new_pet public.pets;
  feeding_time jsonb;
begin
  select household_id into target_household_id
  from public.household_members
  where user_id = auth.uid()
  limit 1;

  if target_household_id is null then
    raise exception 'No household for this user';
  end if;

  insert into public.pets (household_id, name, breed, sex, birthdate, birthdate_is_approximate, photo_url)
  values (target_household_id, pet_name, pet_breed, pet_sex, pet_birthdate, pet_birthdate_is_approximate, pet_photo_url)
  returning * into new_pet;

  for feeding_time in select * from jsonb_array_elements(feeding_times)
  loop
    insert into public.feeding_schedules (pet_id, scheduled_time, label)
    values (
      new_pet.id,
      (feeding_time ->> 'scheduledTime')::time,
      (feeding_time ->> 'label')::public.feeding_schedule_label
    );
  end loop;

  return new_pet;
end;
$$;
```

Three things that are deliberate:

- **`security invoker`.** The `pets` table already has an `Owners can create pets` insert policy and
  `feeding_schedules` has the matching one. Running as invoker means a Contributor calling this is
  refused by RLS, which is correct and needs no code. `create_household_and_pet` is invoker for the
  same reason — read the header of `20260723090100_fix_create_household_and_pet_rls.sql`.
- **`returning * into new_pet` is safe here**, unlike in the households insert. The pets SELECT policy
  is `is_household_member(household_id)`, which is already true for the caller before this statement
  runs. That migration's header explains the case where it is not.
- **No household argument.** The caller's household is derived. An argument would only be a second
  thing to validate.

Revoke execute from `anon`, grant to `authenticated`.

### Deleting a pet needs no RPC

`pets` already has an `Owners can delete pets` policy, and every child table cascades:
`feeding_schedules`, `feed_logs`, `care_cards`, the care-card contacts table, and `pet_photos` all
declare `references public.pets(id) on delete cascade`. One delete does all of it.

**But the storage objects do not cascade.** `pet_photos` rows vanish; the files in the bucket stay,
orphaned. Task 7 deals with it.

### Verify

```sql
select add_pet('Test', 'Kelpie', 'female', '2020-01-01', false, null,
  '[{"scheduledTime":"07:00","label":"morning"}]'::jsonb);

select id, name from public.pets;
select pet_id, scheduled_time, label from public.feeding_schedules;
```

Expect two pets and the new schedule row.

**Revert:** `delete from public.pets where name = 'Test';` then confirm the schedule row went with
it — that also proves the cascade before Task 7 relies on it.

## Task 2 — Service

`src/services/pet.service.ts`.

- **Delete `getForHousehold`.** It is the `.limit(1)` "oldest pet" read and it is the thing being

## Task 3 — Hooks

`src/hooks/queries/use-pet-mutations.ts`:

- `useAddPet` — invalidate `['pets', householdId]`. Toast `SuccessMessage.PetAdded`.
- `useRemovePet` — invalidate `['pets', householdId]`. Toast `SuccessMessage.PetRemoved`.

Both put their toasts in the hook's own callbacks. Removing a pet navigates away from pet detail
immediately, so a callback passed to `mutate()` would be dropped — AGENTS.md explains why.

`useRemovePet` must also invalidate `['slot-states']` and `['feed-logs']`, or Home and Activity keep
rendering a pet that no longer exists.

## Task 4 — Retire `usePet()`

Delete `src/hooks/queries/use-pet.ts`. ADR 0015 names four call sites and says they must move
together. They do:

1. **`home/index.tsx`** — becomes `usePets()`. Task 5.
2. **`activity/index.tsx`** — Task 9.
3. **`log-feed-sheet.tsx`** — takes `petId` as a prop. Task 8.
4. **`notification-settings.tsx`** — the easy one. It uses `usePet()` **only** to interpolate a pet
   name into copy, and its own toggle description already reads "Know when someone feeds a pet".
   Make the two other strings match that generic wording and drop the hook entirely. Do not add a pet
   picker to a notification screen; the preference is per-member, not per-pet.

Do not leave `usePet` in place "for now". A hook meaning "the oldest pet" is exactly the bug this
ticket exists to remove, and something will quietly keep using it.

## Task 5 — Home, with every pet

**Invoke `/frontend-design` and `/expo-native-ui` first.**

Today: date, the pet's name as a 32pt header, that pet's slot rows, then a Pets tile.

New shape:

- The header is no longer a pet name. Use the date, or a household greeting — decide with
  `/frontend-design`, do not guess.
- **One `PetSection` per pet**, in `created_at` order: the pet's name and avatar, then its slot rows
  for today. Tapping the header opens `/home/pet/{petId}`.
- Each section fetches its own `useSlotStates(petId, today, { live: true })`. Put that call **inside**
  `PetSection`, not in a loop in `Home` — hooks cannot be called in a loop.
- **Zero pets is now reachable** (Task 7 allows deleting the last one). Render an empty state with an
  Add a pet action. Today `PetService.getForHousehold` uses `.single()` and would throw; `usePets()`
  returns `[]` and does not.
- **One pet must not look worse than it does today.** Most households have one pet. If a single
  section with a name header reads as heavier than the current layout, collapse the section chrome
  when `pets.length === 1`.

**The Pets tile stays, repointed.** `buildHomeTiles` currently hardcodes the oldest pet's id and
links to that pet's detail — the only way in before sections existed. It now points at `/home/pets`
(Task 6), so it no longer needs a `petId` at all. Change the signature accordingly.

`PetStack` stays as the tile art and gets more honest, since it was already drawing up to three
avatars for a household that could only have one pet.

Keeping the tile is deliberate: `TileGrid` is the seed of the widget-style Home in the backlog, and
deleting its only tile would leave an empty grid and no example of the pattern.

The notification-permission effect currently keys off `pet?.id`. Re-key it off "the household has at
least one pet" so it still fires once, and keep the comment explaining why the ask lives on Home.

## Task 6 — The Pets screen, and adding a pet

**Invoke `/frontend-design` and `/expo-native-ui` first.**

### 6a. The Pets screen

Route `src/app/(protected)/(tabs)/home/pets.tsx`, reached from the Pets tile.

**This screen manages the set of pets. It is not a way to view one.** That distinction is the whole
reason it and the Home sections can both exist without being the same screen twice:

- **Home section header** → that pet's detail page. Viewing.
- **Pets tile** → this screen. Adding, removing, and eventually reordering.

So: a row per pet with avatar and name, an **Add a pet** action, and remove per row for Owners.
Tapping a row should *not* silently become a second route into pet detail — if `/frontend-design`
wants a row to be tappable, it opens that pet's management options, not its profile.

**On the tension with ADR 0015.** That ADR rejected a pets list screen, and this is not a reversal.
It rejected a list as *the route to a pet* — "a wasted tap" when Home could link straight there. Home
now does link straight there, via the section headers. This screen does a job the sections do not.
Say so if anyone asks; do not quietly contradict the ADR.

### 6b. Adding a pet

Route `src/app/(protected)/(tabs)/home/add-pet.tsx`, reached from the Pets screen and from the
popover's `Add a pet` row.

**Reuse, do not re-write.** `(onboarding)/pet-details.tsx` already has this exact form: the photo
picker, `petDetailsSchema`, `TextInputValidated` for name and breed, `DropdownPickerValidated` for
sex, `DateTimePickerValidated` for birthdate, and the approximate toggle. `(onboarding)/feeding-schedule.tsx`
has the times.

Preferred: extract the form body into a shared component both routes render. If that turns out to
drag onboarding's store into the new screen, copy the form instead and say so — a shared component
that needs `useOnboardingStore` is worse than two.

Differences from onboarding:

- **Do not write to `useOnboardingStore`.** It is onboarding's staging area; this screen submits
  directly.
- Two steps, pet then times, in one flow. A `Tray` (`src/components/core/tray.tsx`) is the standard
  presentation for a sequenced edit — see [ADR 0014](../../adr/0014-tray-is-one-sheet-with-swapping-content.md).
  Use it unless `/frontend-design` says a pushed route reads better for something this substantial.
- On success, navigate to the new pet's detail screen. It is the confirmation.

Enable `Add a pet` in `src/components/ui/create-actions.ts` and point it here. Leave
`Invite someone` and `Edit schedule` disabled — CRU-008 owns the first.

## Task 7 — Remove a pet

**Invoke `/frontend-design` first.** This is destructive and irreversible.

Two entry points, one shared confirmation and one shared mutation: `home/pet/[petId].tsx` and a row
action on the Pets screen. Owners only, both places.

The confirmation must say what is actually lost, by name: every feed log for this pet, its Care Card,
its photos and its feeding schedule. "Are you sure?" is not enough for a cascade this wide. Type the
pet's name to confirm if `/frontend-design` supports it.

**Clean up storage before deleting the row.** `pet_photos` rows cascade away, but the files stay in
the bucket forever, and once the rows are gone nothing knows the paths. So: read the pet's photos,
remove the objects (`PetPhotoService` already has `removeByPublicUrl` and path helpers — reuse, do
not reimplement), then delete the pet. If object removal fails, still delete the pet and log it —
orphaned files are a cost, a pet you cannot remove is a bug.

Deleting the **last** pet is allowed. It lands on Home's empty state from Task 5. Do not block it —
blocking would mean a household could never fix a pet added by mistake.

Navigate back on success — to Home from pet detail, and stay put on the Pets screen, since that one
survives its own list shrinking. Removing the pet whose detail screen you are on cannot leave you
there.

## Task 8 — Log a feed knows which pet

`LogFeedSheet` currently calls `usePet()`. It takes a required `petId` prop instead.

Both call sites of the popover's `Log a feed` primary action assume one pet:

- **Home** — the pet is known from the section, so log from within a `PetSection`. With one pet the
  popover action can stay, passing that pet's id. With several it cannot guess: either it presents a
  pet picker first, or the section is the only entry point. Prefer the section — a picker is a tap
  that the layout already answers.
- **Activity** — no pet context at all. With several pets this action needs a picker or must be
  disabled. Decide with `/frontend-design`; disabling is acceptable given Activity is under review.

`FeedLogDetailSheet` also takes `petId`. It has one from the log itself — `FeedLog` already carries
`petId` (`src/services/feed-log.service.ts`). Use the log's, not the screen's.

## Task 9 — Activity stops hiding pets

**Minimum change. Do not redesign this screen.**

`useFeedLogs(pet?.id)` filters to the oldest pet, so a second pet's history is invisible. Two edits:

1. **`FeedLogService.listPage`** currently does `.eq('pet_id', petId)`. It needs a household-wide
   variant: select logs for all pets in the household. Keep the cursor pagination exactly as it is.
2. **`FeedLogRow`** must name the pet. Two dogs in one list with no pet named is worse than the
   current filter — it looks like double feeds.

`ActivityDayHeader` takes a `petId` — check what it does with it before changing anything. If it
renders that day's slot summary for one pet, it either becomes per-pet or comes out of the list. Read
it, don't assume.

Everything else on that screen — the deep-linked `logId` handling, the empty state, the pagination —
stays exactly as it is.
